## Results

### Dashboard (`GET /reports/summary?from=2026-01-01&to=2026-12-30`, budget p95 < 300ms)

| Scenario | p50 | p95 | p99 |
| --- | --- | --- | --- |
| `GET /reports/summary` | 17.7ms | 25.8ms | 30.2ms |

All figures are produced by five aggregate SQL statements (no N+1) issued concurrently; the payload
reports `newLeads=1`, three open stages, `winRate=0.6` and six forecast buckets for this dataset.

## Query plans (`EXPLAIN (ANALYZE, BUFFERS)`, 5,000 deals)

Deals by stage / pipeline value:

```
GroupAggregate (actual time=3.044..3.616 rows=3)
  Group Key: s.position, d.stage_id, s.name
  -> Sort (Sort Key: s.position, d.stage_id, s.name; quicksort 336kB)
       -> Hash Join (d.stage_id = s.id; rows=4000)
            -> Seq Scan on deals d (actual time=0.012..0.843 rows=4000)
                 Filter: created_at in range AND org_id = … AND status = 'OPEN'
                 Rows Removed by Filter: 1000
            -> Hash (5 stages, stages_org_id_id_key)
Execution Time: 3.764 ms
```

Win rate:

```
Aggregate (actual time=0.628..0.628 rows=1)
  -> Seq Scan on deals d (actual time=0.008..0.573 rows=1000)
       Filter: closed_at in range AND org_id = …
       Rows Removed by Filter: 4000
Execution Time: 0.647 ms
```

Notes:

- Each request runs one query per figure (no N+1); the stage query joins only the org's stages.
- At 5,000 rows the planner deliberately chooses sequential scans because they are cheaper than the
  available indexes (sub-4ms execution). The specified indexes `(org_id, status, closed_at)`,
  `(org_id, expected_close)` and `(org_id, owner_id)` remain in place and serve selective filters and
  larger datasets; no schema change was made based on a 5k-row plan.
- The no-op cache of feature 004 is bypassed by design; 007 introduces the 60s Redis payload cache.
