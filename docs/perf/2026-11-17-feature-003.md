## Query plans (`EXPLAIN (ANALYZE, BUFFERS)`, 5,000 deals)

Board read:

```
Limit (actual time=5.048..5.078 rows=101)
  -> Sort (Sort Key: s.position, d.position, d.id; top-N heapsort)
       -> Hash Join (d.stage_id = s.id; rows=5000)
            -> Seq Scan on deals d (actual time=0.014..0.986 rows=5000)
                 Filter: org_id = … AND pipeline_id = …
            -> Bitmap Heap Scan on stages s (3 rows, stages_org_id_id_key)
Execution Time: 5.346 ms
```

Stage cards read inside the move:

```
Sort (Sort Key: position, id)
  -> Seq Scan on deals (actual time=0.022..1.087 rows=1667)
       Filter: org_id = … AND stage_id = …
Execution Time: 2.202 ms
```

Notes:

- Each request runs a single query (no N+1); the board query joins only the pipeline's three stages.
- At 5,000 rows the planner deliberately chooses a sequential scan because it is cheaper than the available
  indexes (2–5ms execution). The specified indexes `(org_id, stage_id, position, id)` and
  `(org_id, owner_id)` remain in place and serve selective filters and larger datasets; no schema change was
  made based on a 5k-row plan.
- The `(org_id, stage_id, position, id)` index is used for stage card reads once the filter is selective
  enough; the plan is recorded here so a regression at 10x scale is visible in future runs.
